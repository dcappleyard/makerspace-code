# wled_lighting_tools — Lighted Sculpture show runner

Python service on a Raspberry Pi that streams animations to a QuinLED Dig-Uno running **stock WLED** over DDP, on a sunset-based schedule, plus a simulator for developing effects without the hardware.

**[PROJECT.md](PROJECT.md) is the authoritative spec** — hardware, architecture, DDP details, open items, questions, and milestones. Read it before making changes and keep it current when decisions are made.

Key facts (details in PROJECT.md):
- 4 × 50 px 12V WS2811 strings in use = **200 px**. Output 1 (GPIO16): px 0–99; output 2 (GPIO3): px 100–199. A 5th string is a spare, not installed.
- Location is **Madison, WI** (~43.07 N, -89.40 W), America/Chicago.
- WLED firmware is never modified; control is DDP (UDP 4048) + JSON API only. Controller host comes from config, never hardcoded.
- Sculpture: double helix of 10 base pairs, each two "lollipops" (stem + flat ring) on a central rod. `pixels.csv` is generated by `pixel_map.py` (stdlib only) — edit its constants and rerun, don't hand-edit the CSV. Output 1 = 3'→5' strand, output 2 = 5'→3' (`OUTPUT1_STRAND = "3to5"`, confirmed on hardware 2026-11-11). Pixel map, color order and brightness also verified then (PROJECT.md "Hardware bench results"); deployed in Docker on the Pi 2026-11-13.
- Effect interface: `render(t, xyz, meta) -> (N,3)` uint8 or float 0..1; `meta` is `layout.Layout` (labels, masks, derived geometry). Effects live in `effects/` (one module each, `_`-prefixed files are helpers), run through `effects.Player`; keep them pure functions of `t` (use `_util.hash01`, not `random`). Effects can take options: `OPTIONS` defaults + `render(t, xyz, meta, opts)` + optional `prepare(opts)` + `DESCRIPTION`; set via `play.py -o k=v` or a show entry's `options:`; `seed: None` = random per run. Verify new effects in the preview's Source menu.
- A **show** is a named list of effects (and `wled:<id>` presets) in the config's `shows:` section (`shows.py`: `Entry`, `Show`, `load_shows`), with optional per-show `scale`, `minutes_each`, `shuffle`, `transition_seconds`. Each schedule window has a `show:`; `schedule.default_show` covers the rest. A config with only `schedule.rotation` still loads, as a show named `evening`.

Files so far: `wled/ddp.py` (DDPSender + Streamer thread), `wled/api.py` (JSON API, stdlib), `testpattern.py` (bench CLI; procedure in README.md), `pixel_map.py`, `layout.py`, `play.py` (plays one effect), `shows.py`, `schedule.py` + `runner.py` (scheduled shows; deployed on the Pi with `Dockerfile` + `docker-compose.yml`, `restart: unless-stopped`), `web/` (FastAPI dashboard served from inside `runner.py`, three tabs: Scheduler (status, controls via a command queue the loop drains, windows, defaults), Preview (SSE live view + browser-only audition via `web/audition.py`, never sent to the sculpture), Show builder; settings are saved by rewriting the config with ruamel.yaml; static files `common.js`, `scheduler.js`, `preview.js`, `builder.js`, and `sculpture.js`, the 3D renderer shared with the preview), `preview/` (stdlib DDP receiver + SSE, plain-canvas 3D page — no CDN/three.js, works offline; test by pointing `testpattern.py --host 127.0.0.1` at it). Runtime config is the git-ignored `config.yaml` locally, or `data/config.yaml` in Docker (`WLED_CONFIG` env var picks it); `wled.host` is an IP, since `.local` doesn't resolve in the container. The dashboard rewrites only the `schedule:` and `shows:` sections.

Testing without hardware: `runner.py --preview --force-on` (DDP to the preview, API calls only logged), or point `wled.host` at 127.0.0.1 with `wled.api_port` set to a fake JSON server. Use the local `.venv/` (git-ignored) — astral isn't in the system Pythons. PyYAML reads bare `on:`/`off:` keys as booleans; `schedule.py` handles that.

Conventions: follow `../CLAUDE.md` — unpinned `requirements.txt`, no test suite or heavier tooling unless asked.
